# Claim assistant

A spike: questions in your own words, answered with a screen that a language model builds with
[OpenUI](https://github.com/thesysdev/openui) (`@openuidev/react-lang`), from components that run the
engine of the demonstrator. The language model chooses the components and fills in the facts that the
person stated. The knowledge model decides: the cover, the rules with their articles, the next
question, the obligations.

> **Demonstration only. Not insurance advice.** Not made or checked by Zurich. It needs a server and a
> language model, so it is not part of the static demonstrator.

## How it works

```
question ──▶ Claude (system prompt: rules, OpenUI syntax and components, fact catalog)
                │ OpenUI Lang, streamed
                ▼
         Renderer (@openuidev/react-lang) ──▶ components of library.tsx
                                                │ facts, grounded (grounding.ts)
                                                ▼
                                   engine/ of the demonstrator: claim, guide
```

| File | What it does |
| --- | --- |
| `library.tsx` | The components that the model may use: `Answer` (the root), `Note`, `ClaimCheck`, `Verdict`, `Columns`, `Obligations`, `Article`. `ClaimCheck` shows the facts it understood, asks the questions that the decision still needs, and shows the decision of the engine with the `Decision` view of the demonstrator. `Verdict` shows a result of the tool `assess_claim` |
| `tools.ts` | The tool of OpenUI's `Query()`: `assess_claim(facts, changes)` decides on the person's policy, with the changes of a what-if. It grounds both, and gives each result a random proof; `Verdict` shows only results with a proof that the tool issued |
| `grounding.ts` | Checks every fact that the model writes against the policy: the fact must exist, belong to the component's group, and have an allowed value. A certificate fact is always rejected: the policy comes from the certificate that the person chose, not from the model. Rejected facts are shown as "Not used" |
| `prompt.ts` | The system prompt: the rules, the OpenUI syntax and components (generated by the library), and the catalog of the facts with their values (generated from `generated/policy.json`). Byte for byte the same on every request, so it is cached |
| `llm.ts` | The call to the Claude API (`claude-opus-5-5`, low effort, with the server-side refusal fallback) |
| `server.ts` | Builds the app and serves it on 127.0.0.1; `POST /api/answer` streams the answer |
| `fixtures.ts` | Hand-written answers to the five questions of the evaluation. The tests render them; without an API key, the server replays them |
| `evaluation.ts`, `eval.ts` | From an answer to a decision: parse, ground, answer the remaining questions from the test claim, compare with the expected decision. `eval.ts` does it with the real model |

No code of the assistant names an answer or a cover of the product (a test checks it). The product is
in the generated policy, the test claims and the fixtures.

### The what-if: `$facts` and `Query()`

When the policy lacks the module or the option, the model adds a what-if:

```
$facts = {event: "TheftEvent", theftKind: "ItemsStolen"}
check = ClaimCheck($facts)
withItems = Query("assess_claim", {facts: $facts, changes: {hasItemsTransported: "Yes"}}, {status: "open"})
whatIf = Columns([Verdict("With the option items transported", withItems, $facts)])
```

`$facts` is bound in both components: an answer to a question of `ClaimCheck` or of `Verdict` is
written into it, and OpenUI runs every query that uses it again. The model wrote four lines; the
screen keeps two decisions in step while the person answers. This is what structured outputs alone
would not give: the model composes the screen from the results of the engine, and the runtime keeps
it live.

## Commands

From `car-insurance/`:

```sh
bun install
bun run assistant      # http://127.0.0.1:3014/ ; without ANTHROPIC_API_KEY, only the examples, replayed
bun test assistant     # grounding, prompt, tools, and the five evaluation questions; mounted in happy-dom
bun run eval           # the five questions against the language model (needs ANTHROPIC_API_KEY)
```

## What the spike shows, and what it does not

- The OpenUI library is generic: five components, and the catalog comes from the model.
- The decision does not depend on the language model. With the hand-written answers, the five
  evaluation questions give the expected decisions, after the questions that the check asks.
- The step that depends on the model is reading the facts from the question. `bun run eval` measures
  it; it was not run when the spike was written, because no API key was available.
- The what-if runs in a DOM in the tests (happy-dom): the answers go into `$facts`, the query runs
  again, and the what-if decides.
- Not done yet: a conversation over several turns, `Mutation()` (it needs a real action, such as
  saving a claim), and the dates.

## Notes on OpenUI 1.0.1

- The runtime reads `process.env.NODE_ENV`, also as `process.env["NODE_ENV"]`, and expects the bundler
  to replace both. `server.ts` defines them as "production" for the browser build. In a development
  build, the runtime would mount its devtools, which load a script from a CDN.
- The generated prompt says that `$variables` hold only strings or numbers, mentions components that
  are not in this library (`Button`, `Select`, `Form`), and advises mock data when no tool fits. The
  rules of `prompt.ts` override all three; `$facts` holds an object, which the runtime supports.
- The runtime fills `$facts` and runs the queries after the screen is mounted, so a server render
  shows neither. The tests of the bound components run in happy-dom.
- `@openuidev/lang-core` has a postinstall script that sends install telemetry. Bun does not run it
  unless the package is trusted; it is not. Runtime telemetry is opt-in.
